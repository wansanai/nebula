# 批量删除使用 fail-closed 上限与 provider 批量接口

递归删除和多选删除此前都逐个对象串行调用 `delete`,20,000 个对象的目录可能耗时数分钟;同时 `walk_dir` 在 20,000 条时静默截断,`delete_folder` 仍返回成功,可能留下不可见的残留对象。我们决定把删除做成独立的批量执行路径:

- 默认递归删除在 20,000 个对象处 fail-closed:删除任何对象前返回结构化的 `limit_exceeded`;用户显式确认后才以流式方式无上限删除。
- 多选删除不设遍历上限,用户勾选与二次确认已经构成显式授权。
- Provider 暴露 `delete_batch` 与 `max_delete_batch`。确认支持 `DeleteObjects` 的 S3 兼容厂商(AWS / R2 / MinIO / Wasabi / DO Spaces / Scaleway / US3 / JD Cloud / 七牛)复用 `s3-core` 实现,阿里云 / 华为云 / 腾讯云实现各自的批量删除;B2 / 又拍云回退到受控并发的单对象删除。
- 批量删除继续执行、收集每个对象的失败,返回删除摘要;任一个文件删除失败时不删除目录占位对象,避免出现“目录消失但文件残留”。
- 版本化桶保持“删除当前版本、产生 delete marker”的语义,不删除历史版本;确认框需要提示这一点。
- 并发度复用现有 `settings.concurrency`,不新增设置项。

## Consequences

批量接口把 20,000 个对象的删除请求数从 20,000 次降到约 20 次,但需要逐家解析批量响应里的 per-key 错误;B2 / 又拍云等未确认支持批量删除的厂商仍走并发回退。默认上限从“静默部分成功”变为“明确失败”,现有调用方需要处理新的超限结果。递归遍历仍按目录逐层 LIST,因此目录数量极多的前缀仍会在扫描阶段花时间;这次优化的是删除请求,不是遍历协议。

## 2026-11 澄清

20,000 上限实际按 LIST 条目计数,包含 provider 合成的目录项与目录占位对象;UI 因此使用“项 / 扫描上限”而不是“对象”。保护行为不变。
